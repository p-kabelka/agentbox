# Git Sidecar — Repository Sharing

## Transport and isolation

Every session has one `git` Compose service running an unprivileged Git daemon
and a small read-only repository catalog server. It has a read-only root filesystem,
dropped capabilities, a writable `git-data` named volume at `/srv/git`, and only
the session's `internal: true` network. Neither port 9418 (Git) nor 8083
(catalog) is published. The agent never mounts this volume or a host
repository. No writable host-directory bind mounts are generated by default.
Read-only proxy-configuration and preset-dotfile mounts retain their existing behavior.

The daemon accepts upload-pack and receive-pack for bare repositories below
`/srv/git/repos`. Repository initialization uses an empty template; Git services
explicitly disable hooks with `core.hooksPath=/dev/null`. Object checking is
enabled. Manual Git operations retain normal ref-update semantics. Agents can
publish commits and refs, not write the sidecar's configuration, hooks, catalog,
or filesystem. An agent may read or push to any repository shared with its own
session: the session, not an individual repository, is the trust boundary.

The host uses `agentbox::<session-file-URI>#<repository>` remotes when
`AGENTBOX_IMAGE_TAG` is unset or empty, and
`agentbox-<tag>::<session-file-URI>#<repository>` for a non-empty tag.
Git selects `git-remote-agentbox` or `git-remote-agentbox-<tag>` from `PATH`;
tagged helpers are symlinks to the intended installation's `bin/git-remote-agentbox`.
`bin/git-remote-agentbox` is a thin exec wrapper for the private
`agentbox _git-remote-helper URL` command in its resolved sibling CLI.
The CLI implements Git's `connect`
helper protocol, starts the sidecar if needed, and streams upload-pack/receive-pack
through `podman exec -i`.
The file URI identifies session configuration; it is **not** a host bare-repo
path. No SSH keys, published ports, `ext` transport permission, or container
socket inside the agent is needed. Both host binaries must be on `PATH`.
The protocol handler and session/locking/registration helpers all live in
`bin/agentbox`; the wrapper preserves stdin/stdout, exit status, and signals.
Host transfers use the remote's transport, absolute session URI, and saved Compose
image references, not the caller's `AGENTBOX_*` environment. No per-session
installation or interpreter record is needed. Removal and stale-remote cleanup
recognize both tagged and untagged remotes regardless of the current image tag.

## Commands and publication

```text
agentbox init [DIR] [--branch REF] [--no-git] ...
agentbox mount [REPO] [--as NAME] [--branch REF] [-n SESSION_NAME | -s SESSION_ID]
agentbox unmount NAME [-n SESSION_NAME | -s SESSION_ID]
```

`init` shares the main repository as `workspace`, cloned at `/workspace`, and
registers `agentbox-<full-session-id>` on the host. `mount` defaults to the current
repository and its basename, cloning to `/context/git/<name>`. Every host repository
uses that same session-specific remote name. Linked worktrees share one remote and
one sidecar repository: mounting another worktree defaults to the existing share
name and pushes its selected branch there. Additional branches can also be pushed
with ordinary Git from any worktree. Use `--session` when invoking `mount` from a
different project. `workspace` is reserved for `init`; `/context/git` is reserved
for Git shares rather than explicit filesystem mounts.

Names are 1–100 characters total, optionally split into `/`-separated components.
Each component uses lowercase ASCII letters/digits/dots/underscores/hyphens and
starts with a letter or digit. Absolute paths, empty components, `.` and `..` are
rejected. For example, `agentbox mount ~/git/org/repo --as org/repo --session ID`
stores `/srv/git/repos/org/repo.git`, served as `git://git/org/repo.git` and cloned
at `/context/git/org/repo`; manual cloning uses `agentbox-clone org/repo`.
Name/path collisions and unrelated existing remotes fail
without overwriting them. Namespace prefixes can be shared, for example
`forge/org/repo1` and `forge/org/repo2`; only overlapping bare-repository roots
are rejected, such as `repo` and `repo.git/child`. This also applies before
publication, so deleting one share cannot delete another.
Repeating a share with the same name and host repository
pushes again without force. Only the selected commit's branch history and
reachable annotated tags are initially pushed; ordinary `git push` can publish
additional branches/tags. Uncommitted files are not shared. Detached HEADs, tags,
and commit IDs use `snapshot-<12-hex-commit>` branches. Worktrees, bare repos, and
SHA-1/SHA-256 object formats are supported. Submodule repositories and LFS payloads
are not implicitly synchronized.

The host creates the bare repository through exec, registers the host remote and
share, pushes, and only then creates its `git-daemon-export-ok` publication marker.
Each GET of `/manifest.json` enumerates those markers and returns repository names;
the namespace walk stops at real bare-repository roots, including unpublished
ones, and never scans their objects or refs. Namespace components ending in
`.git` remain valid. There is no stored manifest, watcher, or periodic scan.
The daemon serves only marked repositories, including for explicit named clones.
A failed push never advertises an empty or incomplete clone;
rerunning the command retries it. Neither host nor agent history is force-reset.

The Git daemon accepts pushes only to existing bare repositories; sandbox clients
cannot create a new sidecar repository. A sandbox-created project can nevertheless
publish its independent history as a new branch in an existing share, for example
`git push git://git/workspace.git HEAD:refs/heads/new-project`. On the host, fetch
that branch or clone it separately with `git clone --single-branch --branch new-project
"$(git remote get-url agentbox-SESSION_ID)" ../new-project` from the original host
project. This creates a separate host checkout, not a separate sidecar repository.

## Startup and manual cloning

Before launching the requested command, the entrypoint copies read-only preset
dotfiles once and runs `agentbox-clone --wait 80`. This reads the catalog and
clones current shares using `git://git/<name>.git`: `workspace` into `/workspace`,
other shares into `/context/git/<name>`. The bounded startup wait handles sidecar
readiness; the process exits after cloning. No watcher, background polling, or
automatic discovery runs while the agent is active. Git and catalog requests are
direct internal traffic, excluded from HTTP proxy settings.

`agentbox mount` may publish another repository while the agent is running, but
does not change the running sandbox's filesystem. Run `agentbox-clone NAME` inside
that sandbox to clone it explicitly; named clones do not query the catalog.
Running `agentbox-clone` without names reads the catalog once and clones all
missing shares. Manual calls exit on failure by default; only `--wait SECONDS`
enables bounded retries. This needs neither exec into the krun VM nor SSH: the
developer or agent runs the helper in its existing shell.

Existing repositories and nonempty destinations are left untouched, including
uncommitted edits. Subsequent host pushes require an explicit fetch/pull in an
existing sandbox clone; there is no automatic merge, reset, or branch switch.
The catalog contains repository names only. Publication sets the bare repository's
symbolic `HEAD` to the selected branch; ordinary clones follow it, and `origin`
points to the sidecar.
`push.autoSetupRemote` allows publishing new branches with `git push`.

## Lifecycle and other configuration

`git-repositories.json` in the session directory maps share names to absolute host
Git common directories, so linked worktrees have one registration. Branches live
only in Git and remote names are derived from the full session ID. Sharing never
rewrites `compose.yaml`. The Git service has a deterministic session-specific name.
The session synchronization lock protects configuration, credentials, and service
lifecycle operations, not Git sharing or transfers. `init` releases it before the
initial workspace push; `mount` and host Git push/fetch never acquire it. Large
packs therefore do not delay `proxy reload`, `stop`, or `remove`. Teardown may
interrupt any Git operation rather than waiting for it. Sharing is not a
transaction with teardown: interruption can leave an unadvertised repository or
a stale host remote. Retry an interrupted share after a stop; after removal, use
`remote-cleanup` if needed. A separate `.git-repositories.lock` serializes
registration, publication, unmount, and session removal metadata operations.
The lock covers the registry read-modify-replace operation, not pack uploads;
different repositories can upload concurrently. Publication rechecks registration
so an interrupted upload cannot republish an unmounted repository.
Internal pushes reuse the already-started sidecar rather than restarting it if
teardown interrupts publication. All service startup uses `--no-recreate` so user
Compose edits cannot destroy a running/persistent agent.

Fetching, review, and merging on the host are manual; agent exit never fetches.
Ephemeral teardown removes containers/networks but retains the named Git volume
and session registration. The next start clones the retained repositories again;
unpushed changes in the removed agent are lost. Persistent teardown stops all
services, including the namespace holder, and retains both the Git volume and the agent's working trees/home.
Host Git can start just the sidecar after either form of teardown, reusing its
existing data, and leaves it running after the transfer. No running agent or proxy
is required. `remove` alone deletes the named volumes and matching registered
remotes in every shared host repository; repointed remotes are not removed.
Fetch wanted commits before removal, especially for a running session.

`unmount NAME` deletes only that repository from `/srv/git/repos`, including its
publication marker and Git objects, removes its host registration, and removes
the matching session remote from the registered Git common directory. Linked
worktrees therefore lose the same shared remote; repointed remotes are preserved.
It accepts `workspace` as well as reference names and starts only the Git sidecar
if necessary. Compose configuration and existing host/sandbox working trees are
unchanged. The name can be reused in a later mount.

Unmounting reclaims the repository's named-volume storage, not just visibility.
The sidecar has a read-only root filesystem, so mounting/unmounting does not
accumulate repository copies in container layers. Active transfers may be
interrupted, and open files can delay reclamation until their processes exit.
Existing sandbox clones remain accessible locally; their content cannot be
revoked, and they keep their own storage. Fetch wanted sidecar-only commits and
retain them in local branches/tags before unmounting: removing the host remote
also removes its remote-tracking refs.

`--no-git` explicitly selects the existing writable host bind mount at `/workspace`
instead of Git isolation. Without it, a non-Git project gets an empty local workspace.
`--ro-mount`, `--rw-mount`, OAuth volumes, and custom certificate mounts remain
explicit opt-ins. Read-only dotfiles and proxy-config bind mounts are unchanged;
the sidecar does not transport configuration or credentials.

## Verification

`tests/test_git_sidecar.py` exercises real Git packs/clones, including detached
HEADs, worktrees, bare/SHA-256 repos, collision handling, catalog validation,
one-shot/manual cloning, bounded startup retries, interruptible transfers,
manual fetching, sandbox-created project retrieval, stable Compose configuration,
worktree-shared remotes, concurrent uploads, publication markers, and unmount/remote cleanup,
substituting only the Podman boundary.

After building `base network git proxy`, run real containers with
`AGENTBOX_INTEGRATION=1 python3 -m unittest discover -s tests -p test_git_sidecar_integration.py -v`.
These tests cover manual cloning of later shares, retained-container restarts, normal Git daemon
operations, isolation, and volume/remote cleanup. They require working native
container TCP/DNS networking and KVM for the default krun runtime; an explicit
`AGENTBOX_TEST_RUNTIME=crun` tests ordinary containers instead. A nested sandbox
booted with `tsi_hijack` cannot provide ordinary Podman bridge networking.

Set `AGENTBOX_TEST_USE_PASST=1` to run the managed guests with passt. This also
checks a blocking receive concurrent with a write on the same Git socket—the
pattern that deadlocks affected TSI firmware—and a 4 MiB native Git push/clone
round trip. Passt needs the runtime procfs setup fix in
[crun #2334](https://github.com/containers/crun/pull/2334).

For the KVM-independent host-to-sidecar transport/lifecycle check only, add
`-k host_transport` to the integration-test command. It verifies multiple shares,
push/fetch, named-volume retention across teardown, Git-only restart, and removal.
